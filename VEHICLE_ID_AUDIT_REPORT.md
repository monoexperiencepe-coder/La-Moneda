# Auditoría crítica — `vehiculos.id` vs número de unidad

**Fecha:** 2026-06-23  
**Empresa auditada:** `07593982-08e6-450c-8abe-4bf590609dd7`  
**Alcance:** Solo lectura. Sin cambios en BD, secuencias, PKs ni migraciones.

---

## Resumen ejecutivo

| Pregunta | Respuesta |
|----------|-----------|
| ¿`vehiculos.id` es PK técnica? | **Sí** — `bigint generated by default as identity primary key` |
| ¿Se usa como número visible de unidad? | **Sí** — en formularios, historial, reportes, copiloto, auditorías |
| ¿Existe `numero_unidad` en `vehiculos`? | **No** |
| ¿Por qué la unidad nueva es #178 y no #83? | La secuencia de identidad **no reutiliza** IDs; hubo **~95 altas históricas borradas** (DELETE físico), por eso el contador llegó a 178 con solo **83 filas** vivas |

**Conclusión:** La app usa `vehiculos.id` como **A + C** (clave técnica **y** número de unidad visible). No hay hoy un campo separado de numeración de flota en `vehiculos`.

## 4. Flujo de creación de vehículo

```
RegistrarVehiculoForm
  → useRegistros.addVehicle
    → vehiculosService.insertVehiculo
      → supabaseMappers.vehiculoToInsert (sin id; solo marca, modelo, placa, anio, color, activo)
      → INSERT en public.vehiculos
      → Postgres asigna id = nextval(vehiculos_id_seq)
```

**No calcula** número de unidad visual.  
**No inserta** en `unidades`.  
**No sincroniza** `vehiculo_numero` automáticamente (eso ocurre aparte vía `upsertInversionGeneralVehiculoValor` si el usuario pone valor de compra).

Tras crear, opcionalmente asigna conductor (`vehicle_id` en `conductores`).

## 5. Diagnóstico — causa probable del salto a #178

1. **`vehiculos.id` es `IDENTITY`** — cada INSERT consume el siguiente entero, aunque luego se borre la fila.
2. **Historial de borrados físicos** — hay **95 huecos** entre id 1 y 178 con solo **83** vehículos vivos → ~95 unidades dadas de alta y eliminadas (o importaciones/pruebas) a lo largo del tiempo.
3. **La UI y el negocio hablan de «unidad #N»** usando ese mismo `id`, por eso el dueño espera #83 (conteo de flota) pero el sistema asigna #178 (contador de secuencia).
4. **Doble señal en inventario:** `listaIndice` (83 en lista) vs `ID 178` en la misma tarjeta — refuerza la confusión.
5. **Tabla `unidades` con 82 filas** vs **83 vehículos** — el vehículo más nuevo (178) probablemente aún no tiene ficha en `unidades` (catálogo legacy no enlazado al alta actual).

### Sobre «82 vehículos visibles»

Al auditar: **83** filas en `vehiculos` (todas activas). La cifra 82 puede corresponder a:
- momento anterior al último alta (id 178),
- conteo de filas en `unidades` (82),
- o filtro de UI distinto al total en BD.

```sql

SELECT
  count(*) AS total,
  count(*) FILTER (WHERE activo) AS activos,
  count(*) FILTER (WHERE NOT activo) AS inactivos,
  min(id) AS min_id,
  max(id) AS max_id,
  max(id) - count(*) AS brecha_max_menos_count
FROM public.vehiculos
WHERE empresa_id = '07593982-08e6-450c-8abe-4bf590609dd7';

-- B) IDs faltantes (muestra)
WITH ids AS (
  SELECT id FROM public.vehiculos
  WHERE empresa_id = '07593982-08e6-450c-8abe-4bf590609dd7'

bounds AS (SELECT min(id) AS lo, max(id) AS hi FROM ids)
SELECT gs AS id_faltante
FROM bounds, generate_series(lo, hi) AS gs
WHERE NOT EXISTS (SELECT 1 FROM ids WHERE ids.id = gs)
```

## 7. Riesgos de cada “arreglo”

| Acción | Riesgo | Veredicto |
|--------|--------|-----------|
| **Resetear secuencia** a 84 | Próximos INSERT podrían **colisionar** si reutiliza IDs aún referenciados en gastos/ingresos/km de unidades borradas; además no corrige datos históricos ya grabados como #178 | **Alto — no recomendado** |
| **Cambiar `id` existentes** (renumerar 1…83) | Rompe FKs en >25k filas; requiere migración masiva y ventana de mantenimiento | **Crítico — prohibido sin proyecto dedicado** |
| **Seguir usando `id` como número visible** | Confusión permanente para el dueño; saltos en numeración; desalineación con Excel «Yaris 01…» | **Medio — deuda UX/documental** |
| **Agregar `numero_unidad` (o similar)** | Bajo si es **columna nueva** + backfill + UI muestra número de flota; `id` sigue siendo PK estable | **Recomendado a medio plazo** |
| **Soft delete en lugar de DELETE** | Evita huecos futuros en conteo de filas, **no** reutiliza IDs de todos modos | Complementario, no suficiente solo |

## 8. Recomendación segura

**Corto plazo (sin tocar PK ni secuencia):**

1. Tratar `vehiculos.id` internamente como **ID técnico inmutable**.
2. En UI de inventario, priorizar **`listaIndice` / conteo de flota** para el dueño y relegar «ID técnico» a tooltip o sección admin (cuando se decida implementar).
3. Documentar al equipo: *«Unidad operativa #83 en pantalla ≠ id de base de datos si hubo bajas históricas»*.

**Medio plazo (solución correcta de negocio):**

1. Añadir `numero_unidad integer` (o `orden_flota`) en `vehiculos`, **único por `empresa_id`**.
2. Backfill: `row_number() OVER (ORDER BY id)` para flota actual → 1…83.
3. Trigger o lógica en `insertVehiculo`: `numero_unidad = max(numero_unidad)+1` por empresa.
4. Cambiar etiquetas UI de `#${vehicle.id}` a `#${vehicle.numeroUnidad}` de forma gradual.
5. Mantener `vehicle_id` en todas las tablas apuntando al **PK `id`**, no al número visual.
